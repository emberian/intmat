# Dense native storage gate

`studies/device_memory_dense.jl` continues the frozen CPU storage study with an alias-preserving target allocator. It instantiates the existing `DeviceCellular` and habitat carriers and runs their existing kernels. The target never holds an intermediate dense carrier: canonical checkpoint validation happens on CPU, followed by direct compact target allocation. Host checkpoint validation still has a dense peak; this is not yet a large-world fresh initializer.

The current resource implementation adds 24 bytes per voxel to the former 268-byte baseline. The specialization uses a single six-column Float32 arena for resource grants and later base/feed transient roles through the core's explicit resource borrow contract. The resulting modeled dense cost is 180 rather than 292 bytes per voxel, before cell state, reduction partials, runtime and allocator overhead. The first three arena columns become scratch only after resource finish. Parallel worlds require disjoint arenas. This is a modeled storage count until native retained and peak measurements are recorded.

The adapter retains all persistent histories densely. Logical unused species and ledger columns read as positive zero; a nonzero or negative-zero write latches the existing status buffer. Uniform mask columns become immutable scalar values; nonuniform columns remain dense and adapt to the device. Bulk checkpoint readout explicitly materializes logical columns without host indexing of GPU elements. Paging remains CPU-only and is not part of this gate.

`studies/run_device_memory_dense.jl` compares complete paired steps, all persistent arrays/counters, and strict canonical restore followed by matching future steps. It records source/runtime pins, actual retained allocation bytes and sysfs VRAM observations. The observations include multiple simultaneous reference carriers and runtime pools, so they are not a single-world peak. No 512³ fit is established: even 180 bytes per voxel alone is 24.16 GB. A 12 GB device requires a smaller dense grid or additional demonstrated storage changes.

Remaining gates are native AMD compilation/parity, full-step timing, nonuniform-mask coverage, peak instrumentation, and a fresh initialization allocator that does not require a dense host checkpoint. Source-pinned production integration follows these gates rather than assuming the CPU proof implies device support.

The bounded CPU driver (8³, capacity 64, source pins in `device-memory-dense-cpu-results.json`) passed both closed and finite-source cases, ten paired steps plus three future steps after strict restore. Actual backing allocations were 572,388 versus 515,044 bytes, a 57,344-byte reduction equal to 112 bytes × 512 voxels. Small-grid timings were 0.882/0.911 ms closed and 1.015/1.004 ms fed (baseline/specialized); these establish functionality, not a device speed claim. The separate test set passed 17 assertions including alias and failure-latch behavior.

The 17-test borrowed-arena suite was rerun against committed recipe 45ce5ab (including the whole-habitat alias guard integrated in 8f502c2): all passed in 83.1 seconds. The canonical host checkpoint round trip remains exact. The native gate snapshot is built from that commit plus this adapter/runner/test, and will record complete source hashes; no native result is implied by this CPU rerun.
